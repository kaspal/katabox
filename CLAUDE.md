# CLAUDE.md

Guidance for Claude (and any AI pair) working in this repo. Read it at the start of every session.

## What KataBox is

A free, open-source, offline desktop app for coding practice (LeetCode/HackerRank style) on Windows and Linux. Users solve problems in Python, JavaScript/TypeScript, PHP and Rust; code runs locally in an OS sandbox and is judged against public and hidden tests. The full plan lives in the "KataBox — Desktop Coding Practice Platform: Build Plan" doc; decisions are summarized in `docs/adr/`.

## Commands

```sh
scripts/fetch-toolchains.sh # Linux: Python + JS/TS into target/katabox via `kb-toolchain install` (.ps1 on Windows: every language; -NoLanguageServers for runtimes only)
cargo run -p kb-toolchain -- list            # what is installed in the dev root (install/uninstall LANG; --root DIR)
KB_REAL_PINS=1 cargo test -p kb-toolchain --release --test real_pins -- --nocapture  # download and check every pin (network; required before changing manifest.toml)
cargo test                       # library crates (default-members); Linux needs libseccomp-dev
cargo deny check licenses        # license check (hakoniwa is an approved LGPL exception)
kb-sandbox probe                 # Linux: what this kernel supports (cargo run -p kb-runner --bin kb-sandbox -- probe)
cargo clippy --all-targets -- -D warnings
cargo fmt --all
cargo run -p kb-pack -- validate # validate every problem, with each problem's compressed test size (budget 512 KB; --run: machine factor, then sandbox checks: validator, reference speed per language, 500-seed stress vs brute.py, naive.py TLE, naive.rs needs ≥ 1.5× the Rust CPU cap (ratio printed; content aims for ≥ 2×), every fix-the-bug buggy file fails; `--run --problems a,b` or `--from FILE` checks only those problems, a base with its follow-ups; Windows)
cargo run -p kb-pack -- generate content/problems/<id> --size max --seeds 1,2  # write hidden tests from gen.py (sandbox; committed)
cargo run --release -p kb-pack -- profile content/problems/<id>  # complexity profile: input hashes + reference times in every language into profile/reference.json (sandbox; committed; ADR 0024)
cargo run --release -p kb-pack -- profile --inputs  # regenerate the gitignored profile input caches from gen.py and verify their hashes (sandbox; the build packs profiles only from these)
cargo test -p kb-judge --release --test complexity_windows -- --nocapture  # profiler calibration set (28 known solutions; prints the hit rate, needs ≥ 85%)
cargo run -p kb-pack -- validate --learn --run  # Learn topics only: structure, then both samples on every case in the sandbox (ADR 0029); --topics a,b or --subject s limits the sandbox part (unknown ids fail); --sets a,b runs reading sets (print outputs, complexity line counts; ADR 0035)
pnpm learn:cases                 # regenerate content/learn/*/*/cases.json from the tracers (Vitest fails when stale)
cargo test -p kb-pack --test learn_samples_windows -- --nocapture  # Learn samples vs tracers in the sandbox (Windows; KB_LEARN_TOPICS=a,b to scope)
cargo run -p kb-pack -- build    # validate, then compile content/problems into target/content.db (--out FILE) and content/learn
cargo run -p kb-pack -- new <id> [--mode function|program|sql]  # scaffold a problem package with TODO(kb-pack) markers (validate refuses them); new-topic SUBJECT ID for Learn; preview PROBLEM_DIR renders statements to target/preview (docs/contributing-content.md)
cargo run -p kb-pack -- pack <dir>... --manifest pack.toml [--assignment assignment.toml] --out x.kbpack  # build a pack (pack rules: one reference is enough; deterministic zip with every file's SHA-256; ADR 0038, 0039)
cargo test -p kb-pack --test pack_hostile  # hostile packs: zip slip, links, bombs, file types, hashes, metadata, markup, names, spoofed ids, assignments (ADR 0038)
cargo test -p kb-app --test packs_hostile_windows -- --nocapture  # pack code stays contained in the sandbox (T8; Windows)
cargo test -p kb-app --test stress_windows -- --nocapture  # stress lab e2e: finds a disagreement, function and program modes (Windows; ADR 0036)
cargo test -p kb-app --test authoring_windows -- --nocapture  # the editor's Check in sandbox (Windows; ADR 0040)
cargo run -p kb-judge -- run two-sum --lang <python|typescript|php|rust> <file>  # judge a file (Windows; --public, --json)
cargo test -p kb-judge --test debug_windows -- --nocapture  # debugger e2e in the sandbox (prints the replay timings; debug_js_windows for JS/TS)
cargo test -p kb-judge --release --test visualize_windows -- --nocapture  # visualizer snapshots, Python + TS: shapes, identity, caps, no user code, cost per stop (ADR 0027)
cargo test -p kb-judge --test nodes_windows -- --nocapture  # ListNode / TreeNode round trips and cycle guards in every language (Windows; ADR 0025)
cargo test -p kb-judge --test calibration_windows -- --nocapture  # calibration benchmark (prints this machine's rounds; re-measure the reference times when it or a runtime pin changes)
cargo test -p kb-bridge          # language servers: fake-server lifecycle; real basedpyright, typescript-language-server, rust-analyzer on Windows (needs the .ps1 fetch)
pnpm install && pnpm build       # UI build (tsc + vite)
pnpm test                        # UI tests (Vitest + Testing Library; includes token contrast and en/es/pt-BR key parity)
pnpm licenses:check              # npm license allow-list (scripts/check-npm-licenses.mjs; mirrors deny.toml)
pnpm versions:check              # app version equal in Cargo.toml / package.json / tauri.conf.json, Cargo.lock refreshed, MSI version per the rule in docs/packaging.md
pnpm dev                         # run the desktop app (needs WebView2 / WebKitGTK 4.1); debug builds use <identifier>-dev data folders ("DEV DATA" badge) and target/katabox as sandbox root, or KATABOX_SANDBOX_ROOT
cargo check -p katabox-desktop   # desktop shell (needs WebKitGTK on Linux); build.rs builds resources/content.db
cargo run -p katabox-desktop --features bindings --bin export-bindings  # regenerate apps/desktop/src/bindings.ts after changing a command or IPC type
pnpm notices                     # third-party notices into src-tauri/resources (release builds refuse the placeholder)
pnpm tauri icon src-tauri/icons/katabox.svg  # every icon size from the master (run in apps/desktop; delete the android/ and ios/ folders it adds), then:
pnpm icon-small                  # icon.ico's 16/24/32 layers and 32x32.png from icons/katabox-small.svg (scripts/lib/svg-raster.mjs; reads the ICO back)
pnpm installer-art               # NSIS sidebar/header BMPs from icons/katabox.svg (committed; re-run after changing the icon)
pnpm release:build -- --bundles nsis,msi  # Windows installers into target/release/bundle (notices first; docs/release-checklist.md)
```

## Rules

- Small PRs, one concern each, with tests. CI must be green before merge; the maintainer reviews every PR.
- **Never change `crates/kb-runner` sandbox code, toolchain download verification, or the CSP in `tauri.conf.json` without the maintainer's explicit sign-off in the PR description.**
- Business logic goes in `crates/`, never in `src-tauri` or React components.
- The UI never touches the file system or spawns processes; it calls typed Tauri commands through the generated `bindings.ts` (never `invoke` with strings). Commands return `Result<T, AppError>` with a stable error code (ADR 0011).
- No network access at runtime except toolchain, pack and update downloads.
- No telemetry, ever.
- Pins (URL, size, SHA-256) change only in `crates/kb-toolchain/manifest.toml`, and only after the real-pins test downloaded and matched them. Installs never execute anything (no npm, no installers) and keep ADR 0015's rules: allow-listed HTTPS hosts and redirects, verify before extract, whole-folder promotion, receipt last.
- Language servers (ADR 0014) run outside the sandbox and **never execute user code**: no build scripts, proc-macros, `cargo check`, interpreters, type acquisition or commands. rust-analyzer never invokes cargo; never add cargo to the bundled Rust toolchain. Server settings and the message policy live in `crates/kb-bridge` (`spec.rs`, `policy.rs`); loosening either needs the maintainer's sign-off.
- Every user-facing string goes through i18n in three UI languages (English, Spanish and Brazilian Portuguese; ADR 0040): add the key to `apps/desktop/src/i18n/locales/{en,es,pt-BR}.json` (keys are typed; the three-locale parity test in `lib/static.test.ts` checks that all three have the same keys, no empty value, and the same `{{placeholders}}` and `$t()` references as English). Content (problems, Learn theory, quizzes, reading items) stays English and Spanish; with the Portuguese UI the `content_lang` setting picks which. Show errors and judge messages by their stable codes (`errors.<code>`, `judge.verdict.<v>`, `judge.message.<code>`). Colors for verdicts, difficulty and status always come with an icon or label, and design tokens must keep the WCAG AA contrast test passing (ADR 0012).
- Workspace state (drafts, notes, snapshots with verdicts, layout and editor settings `workspace.layout`, `editor.keymap`, `editor.font_size`, `editor.language`) and its save rules are in ADR 0013; keep CodeMirror and other heavy code inside the lazy workspace route.
- New data in `user.db` only via a numbered migration: a new `crates/kb-store/migrations/NNNN_*.sql` added to `MIGRATIONS` (today `0001`-`0013`). Never edit a released migration (ADR 0010). New migrations add tables or columns only, add their tables to `TABLES` in `user.rs`, and seed rows in `migration_tests.rs`, which upgrades a realistic database from every earlier version (`real_shaped_db`, `assert_upgrade_keeps`).
- Time limits (ADR 0017): `time_limit_ms` in problem.toml is the base (Rust) limit; languages scale it by their `[time]` table in `language.toml`, and the app by the machine's calibration (0.5-3.0). kb-pack judges at 1.0. A reference must use at most 50% of its language's CPU cap, start-up included; when a function problem's reference is over, kb-pack re-measures the start-up and charges test time plus the fastest start-up seen (`checks::charged_cpu`), which removes start-up noise without loosening the rule. Changing a factor, startup allowance or the benchmark means re-running `validate --run` on every problem (and re-measuring the benchmark's reference times).
- Test data (ADR 0018): each problem's tests must stay within 512 KB compressed (`kb-pack validate` enforces it); keep max tests lean (small values, one max test when it suffices). Tests stay committed as JSON; the build never generates them.
- Complexity profiler (ADR 0024): problems with `naive.py` + `naive.rs` set `profile = true` and `profile_sizes`; gen.py takes an int size (`--n`); `kb-pack profile` writes the committed `profile/reference.json` (sizes, seed, input SHA-256s, reference times); the inputs themselves are a gitignored cache (`profile/inputs/`, 512 KB compressed budget per problem) regenerated and hash-verified by `kb-pack profile --inputs` or `validate --run`. Builds pack a profile only from a matching cache (a mismatch fails; no cache = no profile, with a warning), so builds never need toolchains; the Windows release job generates the caches. Re-run `kb-pack profile` after changing the int branch, the sizes, a reference or a runtime pin. Profiles run through the ordinary judge path (12 s budget, no kb-runner change); the UI always says "Estimated". The fit's rules and the calibration results are in the ADR.
- JS / TS editor mode (ADR 0024): a per-problem toggle (`editor.script.<problem>`) edits the TypeScript entry as plain JavaScript (JavaScript grammar, `Language::JavaScript` language server, a `checkJs`, non-strict tsconfig in `kb-bridge/src/project.rs`); drafts, the judge and the debugger stay TypeScript.
- Node types (ADR 0025): `ListNode` / `TreeNode` (and `[]` of them) travel as JSON arrays (a list's values; a tree's canonical level order with nulls, trailing nulls trimmed). The starter code defines the classes before the function and references must contain the same definitions (kb-pack compares the function's declaration line, `kb_judge::signature_line`). Harnesses build nodes iteratively with the solution's classes without running constructors, write results back, and refuse cycles or shared nodes (`node_cycle`); the shared code is `languages/<lang>/nodes.*`. `check_input` and kb-pack type-check every test value. Keep tree height ≤ 1000 in problems. The Python project config sets `reportOptionalMemberAccess` to "warning" so `node.next.next` is not an error (maintainer-approved; ADR 0014 notes).
- Every tag in a problem.toml needs a display name in `tag.names` of `en.json`, `es.json` and `pt-BR.json` (a kb-pack test checks English and Spanish; the Vitest tag test checks all three).
- Practice features (ADR 0019): "today" is always the user's local date sent by the UI (`lib/today.ts`, `YYYY-MM-DD`); kb-app never guesses the time zone. Day values are stored as calendar dates (`kb_core::Day`). The rules live in `kb-app/src/practice.rs` (pure, unit tested), the queries in `kb-store/src/practice.rs`; review mode never reads or writes drafts.
- Practice modes (ADR 0020): mock-interview locks are enforced in kb-app (`ensure_unlocked` on every locked command; it also covers katas and assignments), never only in the UI; the interview timer is wall-clock (`started_at` + `duration_s`). The export format is versioned (`katabox-export/v2`, which still imports v1; each new section is `#[serde(default)]` with a round-trip test); import validates strictly (size cap, exact format, `deny_unknown_fields`, value checks, settings allow-list), merges in one transaction keeping the newer record, and never executes anything. File dialogs are opened from Rust commands (`tauri-plugin-dialog`), so the webview has no dialog permission.
- Packaging (ADR 0021): installers come from `tauri.conf.json` + `src-tauri/windows/`; uninstall cleanup only calls kb-runner's existing `cleanup` (`kb-app/src/uninstall.rs`). Auto-update stays off (cargo feature `updater`, `tauri.updater.conf.json`) and code signing stays off until the maintainer turns them on; never generate, commit or ask for a signing or updater key. The release workflow runs only on `v*` tags. Keep `@tauri-apps/api` and `@tauri-apps/cli` on the same minor as the `tauri` crate (today 2.12; `tauri build` checks it), and `rust-version` (1.99) at the stable toolchain the repo uses.
- Problems must be original. Never copy statements or tests from LeetCode, HackerRank or similar sites.
- Solutions use each language's standard library only.
- Debugger (ADR 0022): replay only. Every debugger action is an ordinary sandboxed run of the language's debug harness (`languages/python/debug.py.j2`; `languages/typescript/debug.ts.j2` steps the solution through Node's in-process inspector from a worker thread, ADR 0023; `kb-judge/src/debug.rs`); never add sockets, a loopback exemption, a network capability or a kb-runner change for debugging. Harness frames stay hidden (only `solution.*` is traced). The debug run's output budget (`TRACE_BUDGET_BYTES` + `RECORD_ALLOWANCE` + prints) is its `max_output_bytes`; truncate the trace gracefully, never raise the cap. The editor is read-only during a session.
- Learn (ADR 0029): tracers are pure TypeScript teaching content in `apps/desktop/src/learn/tracers/`, the one exception to "business logic in `crates/`"; they never touch I/O, emit i18n narration keys only, and their samples are checked against them in the sandbox by `kb-pack validate --learn --run`. Steps are snapshots with stable item ids; a topic counts as viewed only when its last step is reached by playing or stepping. `learn.viewed` and `learn.last` travel with an export; the scenes use only `--viz-*` tokens.
- SQL problems (ADR 0031): `mode = "sql"`, one SELECT judged by `languages/sql/harness.py` on the Python host (read-only, authorizer, SQLite limits; never loosen them). `Language::Sql` fits only SQL problems and SQL problems take only SQL; SQL has no language server (kb-bridge reports it unavailable) and no debugger, profiler or custom tests. Packages have `schema.sql`, `ref.sql`, `wrong.sql` (caught with Wrong Answer), `brute.py` (`solve(tables)` in plain Python), `validate.py`, `gen.py`, and a `sql-*` pattern. The daily problem and "next problem" never suggest SQL before the user has run or submitted one.
- Katas, rating and study plans (ADR 0033): a kata Submit is judged like Submit but writes only `kata_attempts`, never a submission, status, review, daily pick or draft, and hints, the editorial, submissions, History and notes are locked while it runs (`ensure_unlocked` plus the kata lock on notes). The skill rating is a deterministic replay of the history, never stored; it is a soft weight on the daily problem and next problem that leaves the picks unchanged without rating events and never overrides the start floor or the SQL rule. The rules are pure and unit tested (`kata.rs`, `rating.rs`, `plan.rs`).
- Journal, snippets and search (ADR 0034): failures are tagged from the stored report with a fixed tag set (validated in kb-app), and the journal and reflections follow the interview and kata locks. Snippets merge by their random id, the newer `updated_at` winning. Search everything is `search_all` in kb-app (FTS and escaped LIKE) plus the UI's settings index and bundled guide; nothing leaves the machine.
- Follow-ups, fix the bug and reading exercises (ADR 0035): a follow-up is a full package under `<base>/followups/<n>/` (id `<base>--f<n>`, the base's pattern, unlocked once the base is solved; built-in base ids never contain `--`), harder than its base, enforced by its tests, and distinct from every other problem in the catalogue. A fix problem (`kind = "fix"`) ships `solutions/buggy.py` and `buggy.ts` (PHP and Rust optional); every buggy file must fail the tests and the reference must pass (`validate --run`). Fix problems and follow-ups stay out of the daily problem and next problem. Reading answers are verified by running the code in the sandbox (`validate --learn --run --sets`), and complexity answers by counted line events.
- Stress lab and test builders (ADR 0036): a stress run holds the judge slot (one sandbox user, never alongside a Run, Submit or shrink), keeps to its budget (40 rounds or 60 s) with Stop, and needs no kb-runner change. Without Python, inputs come from the signature-based `kb_judge::randgen` and the UI says they were not checked against the problem's constraints. Builders keep the JSON text as the source of truth; Check runs `check_input` and validate.py (`check_custom`), never a solution.
- Backups (ADR 0037): a backup is the ordinary export written atomically (temporary file, then rename) to the folder the user picked in a Rust dialog; pruning deletes only files whose names match `^katabox-backup-\d{8}-\d{6}\.kbx\.json$` exactly in that folder, beyond `backup.keep`; the backup on exit has a hard 5 s cap and never blocks closing. `backup.*` settings stay on the machine. Focus sessions run on the wall clock (`focus.rs`).
- Packs (ADR 0038) are **security-critical**: loosening any of these needs the maintainer's sign-off, like the sandbox.
  - A `.kbpack` is opened only through kb-pack's extractor (`kbpack/archive.rs`): safe names, plain files only, real-size caps and a compression-ratio limit, an extension allow-list, then every file checked against the manifest's SHA-256 list, and the same structural validation as built-in content (pack rules: one reference is enough).
  - Pack Markdown is always rendered with `Markdown trust="pack"`: no links, images, URLs or raw HTML, KaTeX untrusted with limits; kb-pack also refuses markup in pack text.
  - Pack code runs only through the ordinary judge and tools paths in the sandbox.
  - Pack problems are namespaced `<pack>--<id>`; a pack id is `[a-z][a-z0-9]{2,19}` and may not equal a built-in id.
  - Packs stay out of the daily problem, next problem, placement and plans unless `practice.include_packs` is on; an update needs a newer version; uninstall deletes only the pack's folder and keeps the history.
  - Packs are unsigned: the import preview says so and shows the author as stated and the file's SHA-256.
- Classroom (ADR 0039): an assignment (`assignment.toml` in a pack) is enforced in kb-app (its languages, and with `hints = false` the interview's help locks) while it runs; its results file includes code only when the student opts in and lists exactly what it holds before saving. The hash chain has no key and detects casual edits only; docs and UI must never claim more. Teacher imports are parsed strictly, and the CSV export prefixes cells starting with `=`, `+`, `-`, `@`, tab or CR with `'`.
- In-app editor and pt-BR (ADR 0040): kb-app writes the editor's drafts only under `<local data>/authoring/<id>/` (the UI never touches files); saves are validated with pack rules and Export re-opens the pack exactly like an import. The UI comes in three locales; content stays English and Spanish (see the i18n rule).
- Checks are scoped to what changed: new or changed problems get `validate --run --problems …`, Learn topics `--learn --run --topics …`, reading sets `--sets …`; structure-only `kb-pack validate` is always fine. Never run the whole-catalogue `validate --run` unless the task asks for it. Run a Windows e2e suite only when the code it covers changed, and the attack suites when a judge path, harness or pack loading changes.
- One sandbox user at a time: run sandbox suites and `validate --run` one after another, never in parallel. No load or burner tests; keep the machine's load modest.
- Home and splash (ADR 0041): the session and path rules live in `practice/home/` (pure, unit tested) and use only existing data. **The splash window never gets a capability** (it stays out of `capabilities/`, loads no Tauri API, and `app_ready` ignores other windows). **The splash adds delay only on the first run after an install or update, or in `always` mode**; otherwise it closes as soon as the UI calls `app_ready`, and the 15 s failsafe always shows the main window.
- Record significant decisions as a new ADR in `docs/adr/`.

## Problem package format

See `docs/problem-authoring.md` and `content/problems/budget-pair/` for a complete example: `problem.toml` (with `title_es`), `statement.md`, `statement.es.md`, `hints.md` + `hints.es.md` (3 tiers separated by `---`), `editorial.md` + `editorial.es.md`, `tests/public/*.json` (3-5; 2-4 for a follow-up), `tests/hidden/*.json` (15-40; `{"input": {...}, "output": ...}`), `solutions/ref.{py,ts,php,rs}`, `gen.py`, `validate.py`, `solutions/brute.py`, and `solutions/naive.py` plus `solutions/naive.rs` (always together) when the complexity matters, and then `profile = true` with `profile_sizes` and the committed `profile/reference.json` (ADR 0024). A program problem (`mode = "program"`) reads stdin and its tests are `{"stdin", "stdout"}` (ADR 0028); an SQL problem is described above (ADR 0031). A fix-the-bug problem adds `kind = "fix"` and `solutions/buggy.{py,ts}` (PHP and Rust optional), and a follow-up is the same package under `<base>/followups/<n>/` with `parent = "<base>"` (ADR 0035). Problem scripts never run on the host: kb-pack and the app run them in the sandbox (ADR 0016). `validate --run` must pass before merge; generated tests are committed.
